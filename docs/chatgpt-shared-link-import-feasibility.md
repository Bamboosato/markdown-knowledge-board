# ChatGPT共有リンクからのMarkdown取り込み検討

確認日: 2026年10月2日（日本時間）

文書の実装参照確認: 2026年10月6日。共有リンク取り込みは未実装であり、以下の操作・取得API・テストは提案です。共有ページに関する観測は10月2日の調査結果で、今回の文書追加時には再取得していません。

公開されたChatGPTの返信本文を、URIの貼り付けから新規ノートとして取り込む機能は実装可能です。ただし、今回の例にある「ChatGPTが生成した.mdファイル本体」を共有リンクだけで取得できることは確認できていません。返信本文と生成ファイルを区別する必要があります。

## 共有リンクで確認できた内容

対象: [ユーザー提供の共有リンク](https://chatgpt.com/s/t_6abef691ab2c81918ea2b64a9a5ce896)

- 未認証のHTTP取得は200を返しました。応答はMarkdownではなくHTMLでした。
- HTMLの埋め込みデータには、ChatGPTの返信本文が含まれていました。
- 返信は、41項目をMarkdownファイルにまとめたという案内と、`github-pages-portfolio-initial-build-instructions.md`への参照です。41項目の本文は含まれていません。
- ファイル参照は`sandbox:`で始まる内部URIです。公開HTTPSダウンロードURLではありません。ファイルIDも含まれていますが、IDだけでは内容の取得手段は確定しません。
- アプリ内ブラウザーの未ログイン状態では、共有された返信の案内文は表示されましたが、.mdファイルをダウンロードするリンクは表示されませんでした。
- HTTP応答に`Access-Control-Allow-Origin`はありませんでした。この応答では、別オリジンのWebアプリから直接取得して読み取る方式は利用できません。

以上はこのリンクと今回の確認環境での観測です。ログイン状態でのファイル取得、別の共有形式、Vercelからの取得成功率は未確認です。共有リンクをMarkdownとして読み出す公式APIの保証も、今回調べた公式ドキュメントからは確認できませんでした。

## 実現性と対応範囲

| 取り込む対象 | 判断 | 条件・制約 |
| --- | --- | --- |
| 共有ページの返信本文に書かれたMarkdown | 実装可能 | 公開本文の抽出が必要。ページの内部データ形式の変更に追従する保守が発生する |
| 返信内のMarkdownコードブロック | 実装可能 | 通常の説明文と取り込み対象を区別し、プレビューで確認する |
| 今回の例の生成.mdファイル本体 | 現時点では実現性未確認 | 公開取得経路が確認できない。返信の案内文をファイル本体として扱わない |
| ダウンロード済みの.mdファイル | 既存機能で対応可能 | ChatGPT側でダウンロードできれば、Import Markdownで新規ノートに取り込める |

今回の目的が「41項目を含むファイル本体の取り込み」であれば、返信本文のインポートだけでは要件を満たしません。このリンクについては、まず生成ファイル本体の取得経路の確認が必要です。

## 提案する操作

1. Import Markdownに「共有リンクから取り込む」を追加する。
2. URLを貼り付けて取得する。
3. 取得対象が「返信本文」「コードブロック」「生成ファイル」のどれかを明示する。複数候補がある場合は選択する。
4. タイトル、本文プレビュー、元URLを表示する。
5. 「新規ノートとして取り込む」で保存する。

生成ファイルの取得ができないときは、「共有ページからファイル本体を取得できません。ChatGPTで.mdファイルをダウンロードし、Import Markdownから取り込んでください」と案内します。取得できた案内文を、ファイル本体の代わりに自動保存しない設計にします。

公開された返信にMarkdown本文を直接出力してもらって共有する方法も、ファイル本体の取得を必要としない運用上の選択肢です。

初期版は1回の取得と新規作成に限定する案です。同じURLの再取り込みでも新規IDを発行し、既存ノートを更新しません。元URLは参照用メタデータとして保存する案とし、URLをノートの識別子には使いません。

## 既存実装を利用できる部分

- `src/App.tsx`の`importFiles`が、取り込みと保存、結果表示、未保存編集の確認を担当しています。
- `src/lib/backup.ts`の`parseImportFileContent`は、Markdown取り込み時に新しいIDを発行します。
- `src/lib/note.ts`の`createNoteFromMarkdown`が、空本文チェック、frontmatter解析、ノート生成を担当します。
- `saveNote`による保存を利用できます。URL取得処理と保存処理を分け、プレビュー確認後に1回だけ保存します。

新規作成の仕組みは再利用できます。追加範囲は、URL入力ダイアログ、取得API、共有ページの本文抽出、対象選択とプレビュー、エラー表示、および関連テストです。

## 取得処理の設計案

ブラウザーから自アプリのVercel APIを呼び、そのAPIで共有ページを取得・解析して、タイトルとMarkdown候補を返します。これにより、今回確認したブラウザーのクロスオリジン制約に対応できます。ただし、取得元によるアクセス制限やファイルの権限は、この構成でも解決を保証しません。

- 初期版では`https://chatgpt.com/s/...`の公開リンクを対象とする。`/share/...`等は別途実データを確認してから追加する。
- HTTPS、ホスト名、パス形式を検証する。任意URLの代理取得APIにはしない。リダイレクト先も検証し、内部ネットワークへの取得を防ぐ。
- タイムアウト、HTML取得サイズ、抽出本文サイズを制限する。値は実装前に定める。
- HTML内のスクリプトを実行せず、必要なデータだけを解析する。ページ全体をHTMLからMarkdownへ変換する方式では、メニューやログイン案内が混入するため対象本文に限定する。
- `sandbox:`の参照を、公開ダウンロードURLとして推測変換しない。取得できない添付ファイルを明示する。
- `blob:` URLは生成元ブラウザーのコンテキストに依存するため、貼り付けだけで別のWebアプリやVercel APIから取得できるURLとして扱わない。ダウンロード済みの.mdファイルを既存のImport Markdownで取り込む案内にする。
- ChatGPTのログイン情報を本アプリに渡す方式は初期版に含めない。
- 元ページのHTMLをそのまま表示せず、抽出Markdownを既存の表示経路でプレビューする。
- 共有ページのHTMLや抽出本文をログへ保存しない。診断にはエラー分類、HTTP状態、処理時間を使う。
- APIは`Cache-Control: no-store`とし、保存前はノートDBを変更しない。
- 既存のVercelルートと同じ`export default { fetch(request) { ... } }`形式を利用する。デプロイ後にも取得APIの応答を確認する。

この方式は共有ページの内部形式に依存します。抽出不能になった場合は空ノートを作らずエラーにし、ファイル取り込みへ案内する必要があります。OpenAI APIキーやAIによる再生成を使う方式は、今回の案では必要ありません。

## テスト観点

最初に、機能、非機能、データ、UIの4観点を切り分けます。優先して防ぐ不具合は、生成ファイルと案内文の取り違え、既存ノートや未保存編集の消失、誤った対象の保存、二重保存です。

| 観点 | 検証する意図 |
| --- | --- |
| 機能 | 本文抽出、対象選択、新規作成、保存結果が一致すること |
| 非機能 | 低速通信、取得制限、タイムアウト、オフライン、HTML形式変更で誤保存しないこと |
| データ | 日本語、見出し、表、コード、frontmatterを保持し、新規IDで保存すること。ファイル参照と本文を取り違えないこと |
| UI | 取得対象と失敗理由が分かり、処理中の操作抑止、キャンセル、キーボード、狭い画面での操作が成立すること |

### 正常系

- 公開返信に本文があるデータで、取得内容と保存後の本文を比較する。
- コードブロックや複数候補がある場合、選択した対象だけを保存する。
- 同じURLを再度取り込んでも、新しいIDで作成され、既存ノートが変わらないことを確認する。

### 異常系

- 今回のような生成ファイルへの参照しかないデータでは、本体を取得したと誤表示しない。
- 不正URL、非公開・削除済みリンク、403・404・429・5xx、HTML構造変更、空本文、保存失敗を区別する。
- 外部ホストへのリダイレクト、内部IP、危険なリンクやHTMLを含む入力を拒否または安全に処理する。

### 境界値

- URL前後の空白、空文字、日本語や絵文字、長いコードブロックを扱う。
- 設定する取得サイズ・本文サイズ・タイムアウトの直前、上限、直後を確認する。
- Markdown内のIDや同名タイトルが既存ノートと一致しても、新規作成になることを確認する。

### 状態遷移と非同期処理

- 入力 → 取得中 → プレビュー → 保存中 → 完了の各段階を確認する。
- 取得中のキャンセル、閉じて再表示、別URLで再取得した後に古い応答が到着する状況で、古い内容を表示・保存しない。
- 連打、再試行、保存失敗後の再実行で二重作成しない。
- Draft・未保存編集がある前提で、既存の確認フローと整合し、編集を失わない。

### 実行範囲案

実装時は、取得・解析・ID生成・保存制御の単体テストと、この機能および既存Markdownインポートの対象E2Eを選びます。初期状態を固定したローカルノートDBと共有HTMLの固定データを用い、外部サイトの変動とアプリの不具合を切り分けます。

Chrome・Edge・Firefox・WebKitの入力、プレビュー、保存に関わる対象ケースを順次実行する案です。外部サイトへの疎通は別の少数ケースとし、ローカルとVercelの環境差を確認します。同一ブラウザー環境でスクリプトを並列実行しません。

E2E全件は既定にしません。今回追加する処理と既存取り込みへの影響を基準に選定し、無関係な印刷・クラウドバックアップ等は対象外とします。失敗時は再現入力、初期状態、操作順、エラー分類を残し、データ・環境・実装・観点不足のどこに原因があるかを整理します。

## 今回の実施範囲と次の判断

既存コードの調査、例の共有ページの未認証HTTP取得とデータ解析、アプリ内ブラウザーでの公開表示確認を実施しました。アプリ本体の変更、単体テスト、アプリのE2E、クロスブラウザー確認、Vercelからの取得は実施していません。今回は実現性の検討のため、これらは実装時の検証範囲です。

推奨は、公開返信のMarkdown本文を取り込む機能と、既存.mdファイル取り込みへの案内を組み合わせる構成です。ただし「例のリンクから生成ファイル本体を自動取り込みする」ことが必須の場合は、その取得経路を確認できるまで実装可能とは確定しません。返信本文取り込みを、ファイル本体取り込みの代わりとして扱わないことが重要です。
