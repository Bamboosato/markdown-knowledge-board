# Google Drive バックアップ追加の検討

検討日: 2026-09-30。当日のコードとGoogle公式資料を確認した初期設計案。当時は実装・Google Cloud設定変更・動作テストを行っていない。

## 結論

追加は可能。初期版は **ローカル / GitHub Gist / Google Drive の3つの保存先を提供し、Google Driveには暗号化したバックアップを手動保存・復元する** 構成を推奨する。

Driveの通常フォルダーに、保存操作ごとに新しいバックアップファイルを作る。利用者がDriveから存在を確認でき、以前のバックアップも残せる。自動同期・自動バックアップ・複数保存先への同時保存は初期版の対象外とする案。

バックアップ先の追加は可能だが、選択肢の追加だけでは完了しない。Googleの認可、Drive通信、アカウントごとの状態管理、復元画面への接続が必要な中規模の機能追加となる。

## 現行実装で確認したこと

| 項目 | 現状と追加への影響 |
| --- | --- |
| クラウド保存先 | Git一般ではなくGitHub Gist。`src/components/cloud/GitHubSection.tsx` に専用UIがある |
| データ形式 | `src/lib/backup.ts` の `BackupDocument` version 1。ノート本文、ID、タイトル、タグ、更新日時、ピン情報、カスタムメタデータなどを格納する |
| 暗号化 | `src/lib/cloudCrypto.ts` の AES-GCM / PBKDF2-SHA-256 を再利用できる。暗号化後の上限は4,500,000バイト |
| 復元 | `src/lib/cloudRestore.ts` で形式検証と差分計画を生成。追加・更新・スキップ・競合を判定する。単純な全置換ではない |
| 保存先の記録 | `src/lib/cloudMetadata.ts` はGitHubの数値ユーザーID、Gist ID、GitHub URL、revisionに依存している |
| 通信・認証 | `src/lib/cloudApi.ts`、`api/_lib/cloudBackups.ts`、`api/_lib/authSession.ts` はGitHub用。既存処理をそのままGoogle用に流用できない |
| 同時操作 | `useCloudBackup.ts` には実行中制御とWeb Locksによる排他がある。端末間の排他を保証する仕組みではない |

この追加でバックアップ対象のデータ範囲は広げない。Markdown内の外部画像URLなどは、参照先の実体まで保存することを意味しない。Driveに変えただけで画像やアプリ設定をすべて保管できるとは案内しない。

## Driveの保存方式

| 方式 | 利点 | 制約 | 評価 |
| --- | --- | --- | --- |
| 通常フォルダー + `drive.file` | Drive画面から確認・ダウンロード・削除できる。アプリが作成したファイル等に権限を限定できる | 手動削除・移動・複製への対応が必要 | 推奨 |
| アプリ専用領域 + `drive.appdata` | アプリ専用データを通常のDriveファイルと分離できる | 通常のDrive画面にはファイルが表示されない。ユーザーの手動管理には不向き | アプリ内で完結させたい場合の代案 |

両スコープはGoogle公式資料でnon-sensitiveに分類される。Drive全体への権限は不要。ただし、non-sensitiveでも公開用OAuthアプリの基本的な確認や設定は必要であり、「審査や公開準備が一切不要」とは扱わない。

出典: [Drive APIのスコープ](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)、[アプリ専用領域](https://developers.google.com/workspace/drive/api/guides/appdata)。

通常フォルダー案では、初回保存時に `Markdown Knowledge Board Backups` を作成する。ファイル名は日時と一意なIDを含め、同名だけで検索・識別しない。アプリ識別情報と形式バージョンを付け、取得後に暗号化形式と内容を検証する。ノートのタイトルなどはDriveのファイル名に含めない。

アプリ作成ファイルはAPIで一覧化する。任意の既存ファイルをDrive全体から検索できる前提にはしない。ユーザーが別途アップロードしたファイルの選択や任意フォルダー指定を追加する場合は、Google Picker等の導入を別途検討する。

## 認証・認可の方式

| 方式 | 特徴 | 適した範囲 |
| --- | --- | --- |
| ブラウザーでGoogle Identity Servicesのtoken modelを利用 | ブラウザーからDrive APIを呼ぶ。refresh tokenをサーバーで保管しない。期限切れ時は利用者操作による再認可が必要 | 初期版の手動保存・復元に推奨 |
| サーバーでauthorization codeを交換 | サーバー側でtokenを管理し、refresh tokenによる継続アクセスを設計できる。認証API・保管・失効処理が増える | 継続接続を優先する場合や、将来の自動処理 |

初期版はブラウザー方式を推奨する。アクセストークンはメモリー内に保持し、localStorage・バックアップファイル・ログへ保存しない。GitHub認証とは独立させ、Google Driveだけでも利用できるようにする。Googleアカウントの識別が必要な場合は、安定したsubject IDを利用する設計と追加スコープを確定する。

保存先情報は `provider + accountId` ごとに分離し、アカウント変更時に一覧とキャッシュを破棄する。Googleとの接続解除でローカルノートやDrive上のバックアップを削除しない。「このアプリの接続状態を終了」と「Google側の権限取消」は意味を分けて設計する。

出典: [Token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model)、[Web向け認可方式](https://developers.google.com/identity/oauth2/web/guides/overview)。

なお、サーバー方式を採用しても、それだけではブラウザー内の最新ノートをアプリ終了中に取得できない。自動バックアップは実行タイミングとデータの所在を含めた別要件になる。

## 初期版の操作案

1. バックアップ画面で「ローカル」「GitHub Gist」「Google Drive」を選ぶ。
2. Google Driveを選ぶと、接続状態と対象アカウントを表示する。
3. 「Google Driveに接続」からGoogleの同意操作を行う。
4. 「バックアップを保存」でノートのスナップショットを生成し、既存の暗号化処理で暗号化して新しいファイルとして保存する。
5. 保存成功後に日時・件数・サイズを表示する。復号前の件数表示に必要な情報をDriveへ追加公開するかは別途決める。初期版では件数をローカルの保存完了画面のみで表示してもよい。
6. 復元時はバックアップ一覧から選択し、パスフレーズ入力、内容検証、差分プレビュー、適用の順に進める。

一覧はページングを前提にする。初期版では自動世代削除を行わず、保存が増えることとDrive側で削除できることを説明する。世代数制限・自動削除は必要性を確認して追加する。

新規ファイル方式は、複数端末による上書き消失を避けられる。一方、通信が切れたときは「失敗したように見えるが保存済み」の可能性があるため、操作IDを付けて再照会してから再送する。重複作成を完全に防げるかは実APIで検証し、保証できない場合も既存データは消さない。

ローカルへダウンロードした暗号化ファイルを既存のJSONインポートがそのまま扱えるとは限らない。初期版の保証対象はDrive一覧からの復元とし、暗号化ファイルのローカル復元が必要なら共通復号入口を追加する。

## 実装の分け方

- 共通処理: `BackupDocument` の生成、暗号化・復号、形式検証、復元計画を再利用する。
- 保存先固有処理: GitHubとGoogle Driveそれぞれの認証、一覧、保存、取得、接続解除を分離する。Gist IDやrevisionの形式をGoogleに強制しない。
- 共通画面: 保存先選択と実行状態を共通化し、クラウド接続表示とエラーを保存先ごとに扱う。GitHubの既存APIを一度に全面変更する必要はない。
- 保存先メタデータ: 新しい構造を導入し、既存GitHubの記録を安全に移行する。空の初期状態、旧形式、壊れた記録でもノートには影響させない。
- 容量: 初期版は既存の暗号化後4,500,000バイト上限を維持する案。これは現在のアプリ実装上限であり、Drive自体の上限ではない。拡大する場合は暗号化処理、取得、検証、UIの制限を一緒に変更する。

Google Cloudプロジェクト、Drive API有効化、OAuth同意画面、WebクライアントID、利用する本番・ローカルoriginの登録が必要。サーバー方式ならredirect URIとsecret管理も必要。CSP、Googleスクリプト読込、ポップアップ、プライバシー説明への影響も確認する。

サーバーAPIを追加する場合は、このリポジトリの既存Fetch adapter形式に従い、実デプロイでも確認する。ブラウザー方式ならGoogle用の認証中継API追加は原則不要。

## テスト観点

ケース詳細化の前に、次の観点を確認する。最優先で防ぐのは、別アカウントへの誤保存と復元時のローカルデータ損失。

| 分類 | 正常系 | 異常系 | 境界値 | 状態遷移 |
| --- | --- | --- | --- | --- |
| 機能 | 新規保存、一覧、別端末での復元、既存GitHub・ローカル操作 | 権限拒否、ファイル削除、形式不正 | 初回・既存フォルダー、一覧の次ページ | 未接続→接続→保存→期限切れ→再接続 |
| データ | 本文・日本語・タグ・メタデータ保持、差分判定 | 誤パスフレーズ、改ざん、別アプリのファイル、未対応version | 0件、1件、暗号化後上限の直前・一致・超過 | 復元前後の編集、同一ID・同一日時で内容相違 |
| 非機能 | 暗号化内容のみ送信、秘密情報がログに出ない | オフライン、容量不足、429、5xx、応答消失 | 低速回線、大きなデータ、低性能端末 | 二重クリック、複数タブ・端末、処理中の接続解除 |
| UI | 保存先・アカウント・進捗・結果が判別できる | ポップアップ阻止、同意取消、再接続の案内 | 狭い画面、長いアカウント名、キーボード操作 | 保存先・アカウント切替後に前の結果を表示しない |

実装時はテスト用Googleアカウントと専用フォルダーを用意し、初期状態・投入データ・期待する復元差分を固定する。単体成功後も、接続→保存→切断→再接続→復元の通し操作で状態残存を確認する。同一実機でのスクリプト並列実行はしない。

アプリの単体テストとAPIモックを使うE2Eで異常系・境界値を再現し、実Google接続は別の統合確認で行う。認証とポップアップに環境差があるため、Chromium・Firefox・WebKitの対象フローと、利用対象の実モバイル/PWA環境を選定する。モックだけでGoogle OAuth実連携の成功を保証しない。

ログには操作ID、処理段階、HTTPステータス、時刻を残し、トークン・パスフレーズ・ノート本文は残さない。フレーク発生時は認証期限、通信遅延、保存済み応答の消失、アカウント切替中の古い応答を仮説として切り分ける。

今回のE2E実施範囲は **未実施**。設計検討のみで実装変更がないため。実装後はGoogle Driveの対象フローと影響するGitHub・ローカルの回帰確認を基本とし、共通復元処理を変更した場合に範囲を広げる。全件実行は既定にしない。

## 実装前に確定する事項

推奨案は「通常フォルダー」「手動操作」「ブラウザー認可」「保存ごとに別ファイル」「既存の暗号化・差分復元を維持」。この組み合わせなら既存の資産を活用しながら追加できる。

利用者がDrive画面でファイルを管理する必要がない場合はアプリ専用領域へ変更できる。接続の長期維持を優先する場合はサーバー認可を選ぶ。自動バックアップ、任意フォルダー、保存世代の自動整理、暗号化ファイルのローカル復元は追加範囲として判断する。
