# Google Drive連携・バックアップ・Markdown出力 要件定義

作成日: 2026-09-30

状態: 要件定義。実装・Google Cloud設定・実サービス検証は未実施。

## 1. 目的と文書の位置付け

Google Driveを、アプリ復元用の暗号化バックアップ先、および外部アプリで参照するMarkdownの出力先として追加する。Google Driveへの接続を共通機能とし、既存のGitHub連携と統一したUIで提供する。

本書を今回の調整後の要件とし、[初期検討書](./google-drive-backup-feasibility.md)と相違する場合は本書を優先する。既存GitHub連携は[フェーズ2要件](./phase2-auth-cloud-backup-requirements.md)を参照し、既存動作を維持する。

実装の構成と本番検証への引き継ぎは[実装設計](./google-drive-implementation-design.md)に記載する。

「GitHub」は既存のGitHub Gist連携を指す。「参照用Markdown」は通常の非暗号化 `.md` ファイルを指し、アプリ全体の復元用バックアップとは区別する。

## 2. 合意事項

| ID | 項目 | 要件 |
| --- | --- | --- |
| D-01 | 保存先の追加 | 既存のローカル・GitHub機能を維持し、Google Driveを追加する |
| D-02 | 接続の共通化 | Google Driveの接続状態を暗号化バックアップ・復元とExport Markdownで共有する |
| D-03 | 接続UI | 現行GitHubの接続／接続終了／連携解除UIに場所・見た目・操作体系を合わせる |
| D-04 | 接続条件 | Export MarkdownのGoogle Drive出力は、Google Drive接続済みの場合だけ選択可能とする |
| D-05 | 暗号化バックアップ先 | 初回に自動作成する固定フォルダー **`MKB Backups`** を使用する。出力時のフォルダー選択は設けない |
| D-06 | Markdown出力先 | 既存のExport MarkdownにGoogle Driveを追加し、出力のたびに保存先フォルダーを選択する |
| D-07 | Markdown再出力 | 同じアカウント・同じフォルダー・同じノートは既存ファイルを更新する。別フォルダーでは新規保存する |
| D-08 | 用途の分離 | 暗号化バックアップは復元用、非暗号化Markdownは外部参照用として扱う |

以下では未指定の例外動作を、データ保護と既存動作維持のための初期版要件として具体化する。OAuth方式など実装依存の選択は第12節で分離する。

## 3. スコープ

### 3.1 対象

- 任意のGoogle Drive接続、接続終了、連携解除、再接続。
- 固定フォルダーへの手動暗号化バックアップと、その一覧・取得・安全な差分復元。
- Export Markdownのローカル／Google Drive出力先選択と、Driveフォルダー選択。
- Googleアカウントごとの状態管理、エラー復旧、既存機能の回帰確認。

### 3.2 対象外

- 自動バックアップ、常時同期、双方向同期、アプリ終了中のバックアップ。
- ログイン直後の自動アップロード・自動復元。
- 複数クラウドへの同時出力、全ノートの一括Markdown出力。
- 外部アプリへのソース自動登録、外部アプリ側の更新保証。
- バックアップ世代の自動削除、外部画像・リンク先の実体収集。
- 暗号化ファイルのローカルインポート経由の復元拡張。
- 共有ドライブへの対応。初期版の保証対象は、接続ユーザーのマイドライブ内で書き込み可能な通常フォルダーとする。

ローカルの正本は引き続きIndexedDBとする。Google Driveに接続しなくても既存の編集・保存・ローカル出力を利用できる。

## 4. テスト設計観点

ケース詳細化に先立ち、次の観点を固定する。

| 分類 | 観点 | 優先して防ぐ不具合 |
| --- | --- | --- |
| 機能 | 共通接続、固定先バックアップ、フォルダー選択、更新、復元 | 操作対象のアカウント・フォルダーを取り違える |
| 非機能 | 秘密情報保護、可用性、容量、通信障害、競合、性能 | 平文バックアップ送信、認証情報漏えい、応答消失後の重複書き込み |
| データ | 未保存編集、形式互換性、識別子、外部変更、破損 | ノート消失、別ファイルへの上書き、古い状態での復元 |
| UI | サービス識別、操作可否、処理中、再接続、キーボード、狭い画面 | 成功・失敗・保存先・暗号化有無を誤認する |

| 区分 | 対象 |
| --- | --- |
| 正常系 | 接続、暗号化保存、別端末から復元、毎回のフォルダー選択、同一ノートの再出力 |
| 異常系 | 認可取消、権限不足、削除済み、暗号文破損、誤パスフレーズ、タイムアウト、容量不足 |
| 境界値 | 0件・1件・多数、空本文、上限直前・一致・超過、同名フォルダー・同名ノート、一覧ページ境界 |
| 状態遷移 | 未接続→接続→期限切れ→再接続、アカウント切替、オフライン復帰、出力中の編集・解除 |

重大度は、データ消失・別アカウントへの送信・秘密情報漏えいを「致命」、保存／復元不能や意図しない重複・上書きを「重大」、データに影響しない表示崩れを「軽微」とする。

## 5. 共通のGoogle Drive接続

### 5.1 UIと状態

- アプリメニュー内にGitHubとGoogle Driveの区画を設け、サービス名の見出しで対象を明示する。新しい専用設定画面を必須としない。
- 既存の余白、アイコン、接続状態、処理中表示、警告、解除操作の強調、メニューのキーボード操作に揃える。
- UI文言は現行に合わせて英語とする。以下は表示案であり、最終文言はUI設計時に統一する。

| 状態・操作 | 表示案／挙動 |
| --- | --- |
| 未接続 | `Connect Google Drive` |
| 接続確認中 | 確認中表示。Drive操作を無効化する |
| 接続済み | 対象アカウントを識別できる表示、`Cloud Backup`、`Restore from Cloud` |
| 接続終了 | `Sign out` |
| 連携解除 | `Disconnect Google Drive` |
| 認可期限切れ | 再接続を案内し、Driveへの送信を停止する |
| 一時障害 | エラー内容と `Retry`。オフライン時の無意味な再試行は無効化する |

- GitHubとGoogle Driveは同時接続可能とし、一方の接続終了・障害が他方へ影響しない。
- Google側の接続はバックアップ・復元・Markdown出力で一元管理する。各機能で別々にログインさせない。
- 保存済みのアカウント情報だけで接続済みと判定しない。期限切れ・失効・権限不足を扱う。

### 5.2 操作の意味

- `Sign out` は本アプリのGoogle接続状態を終了し、メモリー内の認可情報を破棄する。Google全体からログアウトする意味ではない。
- `Disconnect Google Drive` はGoogle側の認可取消を行い、本アプリのGoogle接続状態を終了する。
- 認可取消が失敗した場合は「Google側の解除が完了した」と表示せず、再試行またはGoogle側での権限管理方法を案内する。
- いずれの操作でもローカルノート、Drive上のバックアップ、出力済みMarkdownを削除しない。
- 接続終了・アカウント変更時は、他アカウントの一覧・フォルダー選択・進行中の古い応答を現在の状態へ反映しない。
- 認証でページ遷移が必要になる場合、未保存編集を保護する。既存の `Save and Continue` / `Cancel` 相当の確認を用意する。
- 再接続後に操作を続けられるようにするが、アカウントが変わった場合は保存先を再確認する。再接続を理由に自動送信しない。

## 6. 暗号化バックアップ

### 6.1 固定フォルダー

- GD-B01: 接続アカウントのマイドライブ直下へ、初回保存時に **`MKB Backups`** を作成する。名前の大文字・小文字・空白をこの表記に一致させる。
- GD-B02: アプリが管理するフォルダーをDriveのIDとアプリ識別情報で管理する。同名であることだけを理由に既存フォルダーを採用しない。
- GD-B03: 通常の保存先選択UIは設けない。ユーザーがDrive上で名前・配置を変更しても、IDで追跡可能なら同じフォルダーを継続使用する。名前を強制的に戻さない。
- GD-B04: ローカルの記録がない別端末でも、同一アカウント・同一アプリのフォルダーを再検出できること。接続時に空のフォルダーを自動作成しない。
- GD-B05: 複数の管理フォルダーが検出された場合は黙って1つを採用せず、復旧用の候補選択を行う。これは通常の保存先自由選択とは区別する。
- GD-B06: 削除・ゴミ箱移動が確認された場合はその旨を表示し、次の明示的なバックアップ操作で `MKB Backups` を再作成する。権限不足・通信障害を削除とみなして再作成しない。原因を判別できない場合は保存を中止して案内する。
- GD-B07: 復元操作ではフォルダーを再作成しない。存在しない場合は復元対象がないことを表示する。

### 6.2 保存

- GD-B08: 保存対象は既存バックアップが扱うノートデータとする。ノート本文・ID・タイトル・タグ・更新日時・ピン情報・カスタムメタデータ等の既存形式を維持する。
- GD-B09: 未保存編集がある場合は保存して続行するか中止するかを確認し、バックアップ対象を曖昧にしない。開始時点の保存済みデータのスナップショットを用いる。
- GD-B10: ブラウザー内で暗号化し、暗号文のみを送信する。既存の暗号化形式、パスフレーズ検証、紛失時に復元できない旨の案内を再利用する。
- GD-B11: 保存のたびに新しいバックアップファイルを作成し、以前の世代を上書き・自動削除しない。日時と一意な識別子で区別できる名前を付け、ノートのタイトルや本文をファイル名に含めない。
- GD-B12: 初期版は既存の暗号化後 **4,500,000バイト** 上限を維持する。超過時は送信前に説明する。これはアプリ側の上限であり、Driveの容量上限とは区別する。
- GD-B13: 0件のバックアップは空であることを明示して確認する。保存しても以前の世代は残す。
- GD-B14: Driveの作成結果を確認してから成功を表示し、日時・サイズを表示する。件数は保存完了時にローカル情報から表示できるが、暗号化前のノート情報をDriveメタデータに追加しない。

### 6.3 復元

- GD-R01: 固定フォルダー内の管理対象バックアップを新しい順に一覧表示する。ページングに対応し、過去世代を選択できること。
- GD-R02: 対象選択→取得→パスフレーズ入力→復号・形式検証→差分プレビュー→利用者による適用の順とする。
- GD-R03: 既存の追加・更新・スキップ・競合判定を再利用し、安全なマージ復元を維持する。ローカルノートを自動削除しない。
- GD-R04: 誤パスフレーズ・破損・未対応形式・不正データでは、適用前に停止する。名前や拡張子だけで形式を信用しない。
- GD-R05: プレビュー後にローカル内容が変化した場合は再判定し、古い計画で上書きしない。適用中の失敗で部分的な復元状態を残さない。
- GD-R06: 暗号化バックアップは外部アプリの参照用として案内しない。パスフレーズ・鍵をGoogle Driveや外部アプリへ渡さない。

## 7. Export MarkdownのGoogle Drive出力

### 7.1 出力先選択

- GD-E01: 既存の `Export Markdown` に `Local` / `Google Drive` の選択を追加する。
- GD-E02: Google未接続、接続確認中、再認可が必要な場合はDriveを選択不可とする。無効な選択肢に理由と共通の接続操作への導線を示す。
- GD-E03: オフライン・Google障害でも既存のローカルダウンロードは利用可能とする。ローカル側の保存場所の扱いはブラウザーの既存動作を維持し、新たなフォルダー選択APIの導入を要件にしない。
- GD-E04: Driveを選んだ場合は **毎回フォルダー選択を表示する**。前回フォルダーを初期表示しても、選択・確認を省略して自動保存しない。
- GD-E05: フォルダーの選択取消・出力取消ではDriveへ書き込まない。選択時と書き込み直前にアカウント・フォルダー・書き込み可否を確認する。
- GD-E06: 出力対象は現在のノート1件。既存同様、編集中の内容を含む出力用スナップショットを作成する。出力を理由にノートの保存済み状態や未保存フラグを変更しない。

### 7.2 ファイル形式と更新

- GD-E07: 既存の `toMarkdownWithFrontmatter` と同等の内容をUTF-8の非暗号化 `.md` として出力する。ファイル名は現行のタイトル・無題・名前整形ルールを基準とする。
- GD-E08: 認証情報、暗号化パスフレーズ、Drive管理用の内部情報をMarkdown本文やfrontmatterへ混入させない。
- GD-E09: 更新先は **GoogleアカウントID × フォルダーID × ノートID** で識別し、DriveファイルIDに対応付ける。タイトル一致だけで更新先を決めない。
- GD-E10: 同じ組み合わせの再出力では、同じDriveファイルIDの内容を更新する。タイトル変更時も同じファイルを更新し、ファイル名を新タイトルに合わせる。
- GD-E11: 別フォルダーを選ぶと新規保存し、元のフォルダーのファイルを移動・削除しない。以前出力したフォルダーへ戻した場合は、対応する既存ファイルを更新する。
- GD-E12: 別ノートが同名でも互いに上書きしない。複数の対応候補がある場合は曖昧なまま書き込まず、更新先の確認を求める。
- GD-E13: 出力先ファイルが削除済みの場合は明示した上で新規作成できる。別フォルダーへ移動済みのファイルを、今回選択していない場所で更新しない。
- GD-E14: ローカルの対応付けが失われた場合も、Drive上のアプリ識別情報から再検出する。識別できないファイルを無断で上書きしない。
- GD-E15: 新規の未保存ノートにも、同一編集セッション内で安定したノート識別子を使用する。初回ローカル保存後も対応付けを維持できるようにする。出力のたびに別ノート扱いにしない。
- GD-E16: 外部変更を検出した場合は、上書き前に確認する。参照用ファイルの変更をローカルノートへ自動取り込みしない。端末間の同時更新を原子的に防ぐ方式と限界は技術検証で確定する。

### 7.3 外部アプリとの関係

- 非暗号化の本文を保存することを出力UIで簡潔に示す。Driveの共有設定をアプリが自動で公開・変更しない。
- 外部アプリからの取り込み・参照は、そのアプリの対応形式と閲覧権限に依存する。本機能の保証対象は正しいMarkdownファイルをDriveに作成・更新するところまでとする。
- Gemini Notebook等での直接取り込み、ソース登録、更新追従は別途実サービス確認を行い、Markdown対応という理由だけで自動同期を保証しない。
- Markdown内の画像URL、相対パス、Mermaid等は既存出力を維持する。外部アプリでの表示再現やリンク先データの複製は保証しない。

## 8. 通信・競合・エラー処理

- 同じ画面での二重実行を防ぎ、処理段階と結果を表示する。バックアップ・復元・Markdown出力・接続変更の競合操作を制御する。
- 処理中の接続終了を無効化するか安全に中止できる設計とし、遅れて返った応答を別アカウントの状態へ反映しない。
- 通信切断・タイムアウトでは書き込み済みの可能性を考慮する。操作ID等を使って結果を再照会し、無条件の再作成を避ける。確認できなければ「結果未確認」として案内する。
- 401／認可失効、403／権限不足、404／対象不明、容量不足、429、5xxを区別する。無限再試行を行わず、再認可・選び直し・時間をおいた再試行など適切な操作を案内する。
- ブラウザー内の排他制御だけで複数端末間の排他が成立するとは扱わない。新規世代バックアップと、既存Markdown更新の競合条件を分けて実装する。
- フォルダー選択後の削除・権限変更、一覧取得後の削除、再接続中のアカウント変更を再確認する。

## 9. 非機能・互換性

- トークン・パスフレーズ・暗号鍵をローカル永続ストレージ、出力ファイル、ログへ保存しない。サーバーに認可情報を保持する方式を採用する場合は、保管・失効・暗号化方式を別途設計する。
- 接続ユーザーの必要なファイル・選択フォルダーにアクセスを限定する方針とし、Drive全体の読み書き権限を前提にしない。
- プロバイダー・アカウントごとにフォルダーID、ファイルID、最終成功情報を分離する。既存GitHubの記録・セッションを壊さない。
- 390px程度の狭い画面で横スクロールや操作欠落を起こさず、キーボード操作・フォーカス復帰・スクリーンリーダー向け状態通知に対応する。
- 大きなデータの暗号化・通信でも進行状況を示す。具体的な処理時間の目標は対象端末とデータ量を定めて評価する。
- Google連携の公開設定がない環境でもローカル・既存GitHub機能が起動できる。未設定状態を接続済みと表示しない。

## 10. 受入条件

以下の前提データを用意し、ケースごとに初期化する。A/Bは別Googleテストアカウント、F1/F2は同一アカウント内の書き込み可能な通常フォルダー、N1/N2はIDが異なる同名ノートとする。既存GitHub接続の有無、ローカル保存済み／未保存、Drive上のアプリ管理情報も明示する。

| ID | 区分 | 前提・操作 | 検証意図／期待結果 |
| --- | --- | --- | --- |
| AC-01 | 正常系・UI | Google未接続でExport Markdownを開く | ローカル出力可能、Drive選択不可。共通接続の導線がある |
| AC-02 | 状態遷移 | Google Aへ接続後、バックアップとExport Markdownを開く | 両機能で同じ接続アカウントを使用する |
| AC-03 | 正常系 | 管理フォルダーがないAで初回バックアップ | `MKB Backups`を自動作成し、暗号文を保存する |
| AC-04 | 正常系 | AC-03の後に再バックアップ | 同じフォルダー内に別世代を作り、旧世代を保持する |
| AC-05 | 状態遷移 | 管理フォルダーの改名・移動、別端末のローカル記録なし | 同じ管理フォルダーを再検出し、不要な新規作成をしない |
| AC-06 | 異常系 | フォルダー削除／権限喪失／通信障害を別々に再現 | 削除確認時だけ保存時に再作成し、復元時や一時障害時に増殖させない |
| AC-07 | 正常系・データ | 新旧・同一・競合ノートを含む世代を復元 | 差分を表示し、確認後に適用。ローカル固有ノートを削除しない |
| AC-08 | 異常系 | 誤パスフレーズ、破損、未対応versionで復元 | ローカルデータを一切変更しない |
| AC-09 | 正常系・UI | N1をF1へ出力し、再度Export Markdownを開く | 毎回フォルダー選択を表示。F1なら同じファイルIDを更新する |
| AC-10 | 正常系 | N1をF2へ出力し、その後F1へ再出力 | F2では新規作成、F1は元のファイルを更新。両方を保持する |
| AC-11 | 境界値 | N1/N2を同じF1へ出力、N1のタイトルを変更 | 同名別ノートを上書きせず、改名でもN1のファイルIDを維持する |
| AC-12 | データ・状態遷移 | 未保存編集／新規ドラフトを出力し、その後ローカル保存 | 編集中の内容を出力し、出力自体でdirty状態を変更しない。対応付けを維持する |
| AC-13 | 異常系 | フォルダー選択取消、出力直前の書込権限取消 | 取消では書き込まず、権限不足は成功と表示しない |
| AC-14 | 状態遷移 | Aの一覧取得中にBへ切替、Aの応答を遅延させる | Aの候補・完了通知・書込先がBの状態へ混入しない |
| AC-15 | 異常系・非同期 | 保存成功応答だけを消失させて再試行 | 結果照会を行い、無条件の重複作成・誤った成功表示を防ぐ |
| AC-16 | 境界値 | 暗号化後4,499,999／4,500,000／4,500,001バイト | アプリ上限以下を許容、超過は送信前に停止する |
| AC-17 | 境界値 | 0件・1件・多数、一覧ページ境界、長い日本語名 | 空の確認、全世代へのアクセス、内容・表示を確認する |
| AC-18 | 状態遷移 | 両サービス接続後にGoogleだけSign out／Disconnect | GitHub・ローカル・Drive保存済みファイルを保持し、Google出力を無効化する |
| AC-19 | 異常系・競合 | 外部編集・複製・複数端末から同じMarkdownへ更新 | 不明な対象へ無断上書きしない。検出可能な競合を案内する |
| AC-20 | 状態遷移 | 復元プレビュー後の編集、IndexedDB適用失敗 | 再判定と整合性を確認し、古い計画・部分適用による消失を防ぐ |
| AC-21 | 回帰 | 未接続・オフラインでローカル操作、既存GitHub保存・復元 | Google連携追加によって既存機能を阻害しない |

## 11. 検証計画と証跡

- 単体: 形式・暗号化再利用、出力先識別、状態遷移、キャッシュ分離、境界値を確認する。
- 対象E2E: Google接続のモック、バックアップ、復元、Export Markdownと影響する既存メニュー・ローカル／GitHub経路を確認する。全件を既定にしない。
- クロスブラウザー: 認可・フォルダー選択・メニュー・再接続に環境差があるため、Chromium／Firefox／WebKitの対象ケースを選定する。実モバイル・PWAは別枠で確認し、エミュレーションのみならその旨を明記する。
- 実連携: **本番環境でテスト担当者が実施する**。テスト用Googleアカウントと専用データで、実OAuth・フォルダー選択・別端末の再検出・保存／更新／復元を確認する。モック成功で実連携済みとしない。
- 同一実機に対するスクリプトの並列実行はしない。同じDriveファイルを更新するテストも直列にする。
- 単独ケースに加え、接続→保存→出力→切断→再接続→復元の通し操作で状態残存を確認する。
- IndexedDB、ローカル設定、認証状態、Driveテストデータの準備・初期化・後始末を明示する。準備は再利用可能な単位に分ける。
- 証跡には操作ID、時刻、処理段階、HTTPステータス、期待／実際、再現手順を残す。本文・トークン・パスフレーズは記録しない。
- フレークは、認可期限、ネットワーク遅延、遅延応答、結果不明、テスト順序、端末間競合の仮説で整理する。原因をテスト観点不足／データ問題／環境問題／実装問題に分類し、なぜ検出できたか・できなかったかと再発防止を記録する。
- 実施結果には、実施範囲・選定理由・未実施範囲・環境・残課題を記載する。

### 11.1 開発側とテスト担当者の分担

| 担当 | 環境・範囲 | 完了時の扱い |
| --- | --- | --- |
| 開発側 | 公式仕様に基づく設計、単体テスト、Google API・認可・フォルダー選択のモックを使った対象E2E、既存機能の回帰確認 | 開発側検証済みとし、実Google連携は本番検証待ちとして明記する |
| テスト担当者 | 本番環境の実Google連携。認可・再接続・解除、固定フォルダー、毎回のフォルダー選択、作成・更新・復元、別アカウント／別端末、外部アプリでの参照を確認する | 実施した受入条件、環境、証跡、未実施項目、不具合を記録する |

実Google連携の事前実行を、設計・実装着手の前提条件にはしない。実サービス固有の未確認事項は残課題として引き継ぎ、本番検証結果に応じて修正する。開発側の検証完了と実連携の受入完了を区別する。

### 11.2 本番検証への引き継ぎ

開発側は、本番検証前に次を整理してテスト担当者へ渡す。

- 対象URL・バージョン、必要なGoogle Cloud／OAuth／API設定、設定済み・未設定の区別。
- 受入条件IDに対応する手順、期待結果、アカウント・ノート・フォルダー・ファイルの前提状態。
- 実認可の期限切れ・取消、フォルダーへのアクセス、別端末での再検出、更新競合など、モックだけでは確認できない項目。
- 実施ブラウザー・端末・PWAの候補と選定理由、証跡の取得方法、実行順序、テストデータの後始末。
- 通信障害や応答消失など開発側で再現済みのケースと、本番での再現が難しいケースの区別。

本番でも専用のテストデータを使い、既存の利用者データを初期化しない。Google Cloud設定は本番検証開始までに用意する必要があるが、実テストの担当指定だけで設定担当やデプロイ実施まで決まったとは扱わない。

本書の初版作成時は文書確認のみであった。その後の実装と開発側の検証結果は[実装設計](./google-drive-implementation-design.md)に記録する。実Google連携と外部アプリ参照は本番環境でのテスト担当者の確認を待つ。

## 12. 技術設計で確定する事項

次は利用者向け合意を変更せずに、公式仕様の確認とモック検証で設計方針を定める。実サービスでの確認は第11節に従い本番環境でテスト担当者が実施する。実確認が必要な挙動は未検証事項として引き継ぎ、要件達成済みと扱わない。

| 項目 | 方針／確認内容 |
| --- | --- |
| OAuth | 手動操作向けのブラウザーtoken modelを第一候補とし、再接続体験・安定したアカウント識別・権限取消を確認する。サーバー方式が必要なら理由を記録する |
| 権限・フォルダー選択 | `drive.file`とGoogle Picker等を候補とし、選択フォルダーへの作成・同じファイルの更新・別端末での発見が成立することを検証する |
| 接続UIの共通化 | 見た目と状態の扱いを揃える。GitHub専用セッションリセットを、Googleに不要なまま機械的に追加しない |
| 管理情報 | フォルダー／ノート／操作の識別情報をどこへ保持するか、複製時の重複候補、ドラフトIDの継続性を確定する |
| 更新競合 | Driveの条件付き更新・revision等の実際の挙動を検証する。事前取得だけを原子的な排他保証と説明しない |
| 公開設定 | Google Cloud、OAuth同意画面、クライアントID、origin、必要なAPI、CSP、公開に必要な手続きを整理する |
| 配備 | 本番・Preview・DevelopmentそれぞれのGoogle連携可否を定義する。API追加時は既存の配備方式と実環境での応答を検証する |
| 外部参照 | `.md`の取り込みと更新追従は別に確認する。Googleドキュメント変換は現時点の要件に含めない |
