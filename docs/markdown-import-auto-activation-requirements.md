# Markdown／text新規登録後の自動選択 要件・実装結果

- Status: Implemented（ローカル実装済み・検証結果は末尾に記録）
- Updated: 2026-10-02

## 1. 結論

実現可能。ドラッグ＆ドロップまたはファイル選択で新しいノートを登録したとき、現在のノートに未保存変更がなく、保存処理中でもなければ、登録したノートを自動選択する。

未保存変更の消失を最優先で防ぐため、登録開始時と完了時の両方で条件を確認し、処理途中の選択・編集操作があった場合は自動選択しない。ユーザーの実装指示に基づき、検索・タグ絞り込みを維持する案を採用して実装した。

## 2. 実装前の確認

2026-10-02の変更前のローカルコードを静的に確認した。以下の行番号は変更前の位置を示す。

- `src/App.tsx:1805`の`importFiles`はMarkdown／textとJSON backupに共通。新規登録では保存成功後に一覧を更新するが、選択IDとエディタの内容を新規ノートへ切り替えていない（1889〜1903行）。
- ファイル選択は`handleImport`から同関数へ渡す（1923〜1934行）。既定で未保存変更の確認を実施する。
- ドロップの新規追加も`handleAddDroppedFiles`から同関数へ渡す（1952〜1963行）。保存済みノートでは未保存変更を確認し、未保存の新規Draftでは確認なしにDraftを保持して追加する。
- 未保存変更の既存判定は`isDirtyRef.current`または`tagInput.trim().length > 0`（2487〜2507行）。保存中は`saveStatus === "saving"`で表現される。
- `New Note`は文字を入力する前からdirtyなDraftになる（2229〜2264行）。空に見えるDraftも保護対象になる。
- カードのactive表示と`aria-current`は`selectedId`に連動する（4314〜4333行）。エディタ同期には`resetDraft`も必要で、選択IDだけの変更では足りない。
- 通常のカード選択はPreviewへ切り替える（2937〜2950行）。今回の要件は選択変更に限定し、Edit／Previewの強制切替は追加しない案とする。
- 既存E2Eには、新規Draftを維持する単一・複数ファイルの新規追加ケースがある。維持する回帰条件として使用できる。

## 3. テスト観点（詳細ケースより先に定義）

| 分類 | 観点 | 検証意図／優先度 |
| --- | --- | --- |
| 機能 | ドロップ／ファイル選択、更新中判定、選択先、成功件数、対象外経路 | 両導線で条件どおりに選択する。誤った選択変更は重大 |
| 非機能 | 非同期read／save、保存との競合、連続登録、ブラウザー・OS差、大容量、モバイル、オフライン | 遅延完了や環境差で編集中の内容を失わない。競合による消失は重大 |

| UI | activeカード、エディタ同期、Edit／Preview、検索・タグ絞り込み、結果dialog、focus、スクロール | 一覧と表示内容を一致させ、登録結果を確認できる。内容不一致は重大、スクロールのずれは軽微 |

致命的なデータ消失につながる「未保存変更の暗黙破棄」を最初に防ぐ。次に、保存に失敗したノートや別ノートを選択する重大な不具合を防ぐ。

## 4. 推奨仕様

### 4.1 対象

- `.md`／`.markdown`／`.txt`の新規追加。
- Edit／Previewへのドロップで`Add as New Note(s)`を選んだ場合と、`Import Markdown`からのファイル選択。
- JSON `Import Backup`、`Replace Current Note Body`、クラウド復元、`New Note`の動作変更は対象外。

### 4.2 「更新中」の定義

次のいずれかを満たす場合を更新中として、自動選択しない。

1. 未保存変更がある（Title、Body、Tags、Marp、Custom metadataなど、既存dirty判定の対象）。
2. タグ欄に確定前の文字がある。空白のみの入力は既存判定に合わせて対象外。
3. ノートの保存処理中である。

Editタブが開いていても、上記に該当しなければ自動選択する。Previewでも未保存変更があれば自動選択しない。保存に失敗してdirtyが残っている場合や、未入力の新規Draftも自動選択しない。

### 4.3 自動選択条件とタイミング

以下をすべて満たす場合に限り、ファイル群の登録処理が完了した時点で1回だけ切り替える。

- Markdown／textとして、新規保存に成功したノートが1件以上ある。
- 今回の登録処理を受け付けた時点で更新中ではない。ファイル選択はファイル受領時、ドロップは新規追加actionの実行時を基準とする。
- 完了時点でも更新中ではない。
- 受付後に、ユーザーによるノート選択、新規Draft作成、編集操作がない。

処理中に編集し、その後SaveやUndoでdirtyが解消しても、自動選択はしない。単に開始時と完了時のIDやdirtyが一致するだけでは、別ノートへ移動して戻る操作も検出できないため、操作世代などで判定する。

選択がない状態で更新中にも該当しなければ、登録したノートを選択する。中止・ファイル0件・成功0件では切り替えない。

### 4.4 複数ファイルと部分成功

- 受領したファイル配列の順に、最初に新規保存に成功したノートを選ぶ。
- 先頭ファイルが失敗して次のファイルが成功した場合、その成功したノートを選ぶ。
- 他ファイルが失敗しても、成功が1件以上あり条件を満たせば自動選択する。失敗情報は既存の結果dialogに表示する。
- Pinや`updatedAt`による一覧の並び順を選択先の決定には使わない。元から一覧先頭のノートを誤選択しない。
- ファイルごとに画面を切り替えず、全処理の完了後に一度だけ選択する。

### 4.5 既存の未保存確認との関係

今回の最小変更案では、既存のSave／Discard／Cancelの確認フローを維持する。

- 受付時に更新中だった場合、確認でSave／Discardを選び、その後追加に成功しても自動選択しない。開始時の保護判定を保持する。
- Cancelでは既存どおり登録を中止する。
- 新規Draftのドロップ追加は、従来どおりDraftをそのまま保持する。

「更新中でも確認なしで追加し、編集中のノートを保持する」へ全導線を統一する案は、既存の確認・中止動作を変更する別要件になるため、今回の最小変更には含めない。

### 4.6 画面の同期

- 保存成功したNoteを使って、一覧、`selectedId`、Title／Body／Tags／metadataなどのdraftを同期する。新規ノートはdirtyではない状態にする。
- Edit／Previewのactive tabとモバイルの一覧／エディタ表示は維持する。自動で編集を開始したり、Previewへ強制移動したりしない。
- Previewは新ノートの内容へ更新し、Slidesなどノートに依存する表示状態も整合させる。
- 結果dialogの件数、失敗理由、Close／Escape、focus復帰を維持する。dialog表示中に背面カードへfocusを奪わない。
- 一覧が表示されていて選択カードが絞り込みに含まれる場合は、既存のreveal処理でスクロールして見えるようにする。reduced motionに従う。

### 4.7 検索・タグ絞り込み（維持する仕様を採用）

検索・タグ絞り込みを維持する。条件外の新規ノートでも選択IDと内容は切り替えるが、そのカードは絞り込み解除まで一覧に表示されない。絞り込みを解除した時点で新規ノートのカードがactiveになる。

登録後に必ず一覧内でactiveカードを表示するための絞り込み解除は、今回の実装には含めない。

## 5. 実装の追加範囲

主な変更箇所は`src/App.tsx`の新規import共通処理と選択同期。取り込み形式やIndexedDBスキーマの変更は不要。

1. 新規登録受付時に自動選択可否とユーザー操作世代を保持する。
2. `saveNote`成功後に、最初に保存できた新規Noteを記録する。保存前のcandidateや一覧先頭を使用しない。
3. 全ファイル処理後、最新のdirty／タグ入力／保存状態／操作世代で条件を再評価する。
4. 条件を満たす場合だけ新規Noteへ選択・draftを同期する。既存の`handleSelectNote`は確認dialogとPreview切替を伴うため、そのまま呼ぶのは適切でない。
5. ドロップとファイル選択で同じ判定を通し、backupには適用しない。

非同期処理のクロージャに残る古い`tagInput`や`saveStatus`を完了時の判定に使わない。最新状態の参照方法を用意する。連続登録の実行ガードを受付時に確実に適用し、選択待ちdialogの多重起動も防ぐ。

既存の`workingNotes`は処理開始時にDBから取得したsnapshotである。取り込み中に独立した保存操作を許可する場合、完了時の一覧更新でその操作を巻き戻さないことも実装時に確認する。競合する保存を直列化するか、一覧更新を保存成功分の反映に限定する必要がある。

## 7. 実行範囲・証跡・原因切り分け

検討時は静的調査のみ実施した。続く実装段階の実行結果は第8節に記録する。

実装時の検証計画は次のとおり。実際の実行範囲と未実施範囲は第8節に示す。全件E2Eは既定としない。

- unit：抽出した自動選択判定の状態分岐と、成功ノートの選定規則。非同期競合は実際の状態更新を含むテストでも確認する。
- Chromiumの対象E2E：両導線、dirty・タグ・Draft保護、複数件・部分成功・保存失敗、遅延中の操作、結果dialog、絞り込み、対象のモバイル表示。
- Firefox／WebKitの対象E2E：ドロップ／ファイル選択、activeと内容の同期、modal focus復帰、Draft保持。OSネイティブdropはWindowsで別途対象確認する。
- オフラインと大容量による遅延を対象ケースに含める。ローカル登録のためネットワーク到達性を新しい成功条件にしない。
- 未実施範囲：Cloud、PWA、Print／PDFなど無関係な全件E2E。範囲と理由を実装結果に明記する。

同一実機のブラウザー操作は直列に実施する。DB初期化をケースごとに行い、単独成功・通し失敗を防ぐ。競合ケースは固定sleepに依存せず、read／saveの開始・完了を制御する。

登録前後のDB全フィールド、選択ID、draft、dirty、タグ入力、保存状態、tab、絞り込み、処理受付と完了の順序、結果dialog、失敗理由、ブラウザー／viewportを証跡にする。ブラウザーで選択切替を確認しただけでDB成功を推定しない。

失敗は「観点不足／データ問題／環境問題／実装問題」に分類する。フレークは古い状態参照、二重受付、DB初期化漏れ、modal focusとスクロールの非同期競合を仮説として整理し、再現手順と制御可能なタイミングを確保してから結論を出す。

## 8. 実装・検証結果（2026-10-02）

### 8.1 実装内容

- `src/App.tsx`の共通importに実装。最初に保存成功した新規ノートへ、一覧の選択・エディタ内容・Previewの対象・スライド位置を同期する。Edit／Previewとモバイルの表示領域、検索・タグ絞り込みは維持する。
- 未保存変更、未確定タグ、保存中の最新状態を同期的にrefへ保持する。選択・編集・保存の操作世代も記録し、処理中に編集後Save／Revertを行った場合や、別ノートへ移動して戻った場合にも自動選択しない。
- 未保存確認の前からimport受付を予約し、確認待ち・読み込み中の重複受付を抑止する。予約は中止・失敗を含めて解除する。
- Markdown／textの一覧更新は成功分の追加だけを反映し、処理中に保存した既存ノートの内容や一覧からの削除を、開始時のsnapshotで巻き戻さない。
- JSON backupの自動選択は追加せず、本文置換と新規Draftの保護を維持する。保存形式・DBスキーマは変更しない。

### 8.2 実行範囲と結果

同一実機では全E2Eを`--workers=1`で直列実行した。全件E2Eは実施していない。新規追加21ケースと既存登録・本文置換12ケースを中心に、変更したケースと失敗したケースだけを対象再実行した。

### 8.3 検出した問題と原因切り分け

**WebKitのオフライン模擬環境：環境問題。** 最初の失敗では選択カードの検証より前に、結果dialogがAdded 0／Failed 1、理由が`The I/O read operation failed.`になっていた。実ファイル経路へ切り替えても3回とも再現した。アプリを開かず、単純なページ上の`new File(["hello"], "test.md").text()`とファイル入力の読み込みを比較すると、オンラインでは両方成功し、`context.setOffline(true)`では両方とも`NotReadableError`になった。自動選択の処理に到達しない、アプリ外でも再現する制約として切り分けた。

このため、WebKitの通常モバイル登録は実施し、WebKitでのオフライン登録成功は未検証として扱う。Chromium／Firefoxの実ファイルを使うオフライン登録は成功した。WebKitの実端末・実ネットワーク切断時の結果は、この模擬環境から推定しない。

**キーボード保存のタイトル件数：テスト観点不足。** 保存後の同名タイトルが一覧カードと印刷用DOMの2か所に存在し、ページ全体の`getByText`による件数判定が失敗した。トレースで一覧カードは1件、もう1件は`print-surface`内の見出しであることを確認し、検証意図に沿って`.note-list`内の保存カードだけを数えるよう修正した。再実行した2ケースは成功した。表示用DOMと印刷用DOMが重複する検証では、対象領域を明示する。

### 8.4 未実施範囲とリリース状態

- Cloud、PWA、Print／PDFなどの全件E2Eは未実施。変更が登録後の選択と編集状態に限られるため、関連経路を選定した。
- WebKitのオフライン登録成功、実Safari／iOS／Android端末での操作、実ファイル大容量での性能測定は未実施。非同期競合はreadを制御して、固定sleepに依存せず検証した。
- 実装とローカル検証は完了。PR・マージ・配信の結果は、対応するGitHub PRとdeploymentに記録する。
